# Оркестрация задач

Главный агент в чате проекта — ORCHESTRATOR. Он ведёт задачу от ТЗ до готовой к отправке ветки.

## Этапы
1. **Приём.** Проект = проект текущего чата. Создай папку `~/ai-workflow/tasks/<проект>/<id-задачи>/` (id из Active Collab или короткий slug).
2. **Анализ (task-analyst).** Исходное ТЗ → `spec.md`: контекст, цель, текущее и ожидаемое поведение, функциональные требования (FR-1, FR-2…), технические требования, ограничения, критерии приёмки, риски. Всё неясное помечай `[НУЖНО УТОЧНИТЬ: …]` — не выдумывай.
3. **Уточнение.** Сначала ищи ответы в коде и документации. Остались вопросы, влияющие на бизнес-логику или UX, — один список мне, не больше 5 вопросов. Ответы записывай в `spec.md`.
4. **Исследование (project-researcher).** Затронутая часть проекта, похожие реализации, переиспользуемые компоненты → `plan.md`: какие файлы меняем, подход, список шагов. Независимые шаги помечай `[P]`.
5. **Проверка согласованности.** Перед разработкой сверь `spec.md` и `plan.md`: каждое требование покрыто шагом, нет шагов вне ТЗ.
6. **Разработка (developer).** Строго по плану и правилам проекта. Без рефакторинга вне задачи, без новых зависимостей без необходимости, без изменения несвязанных файлов.
7. **Ревью (code-reviewer).** Независимо, по `git diff`, ТЗ и правилам проекта → `review.md`: проблема, критичность, файл:строка, причина, рекомендация.
8. **Тестирование (tester).** Lint, типы, тесты, сборка — то, что есть в проекте. Сверка с критериями приёмки.
9. **Git (git-manager).** Проверка diff, коммит только файлов задачи (см. `git-safety.md`).
10. **Финальный отчёт и остановка.** `report.md` и сообщение мне: что сделано, изменённые файлы, ключевые решения, результаты тестов и ревью, риски, как посмотреть diff. Затем жди моего подтверждения на push.

## Циклы исправлений
- Серьёзные замечания ревью или упавшие проверки → назад к разработчику.
- Не больше 2 автоматических циклов «исправление → повторная проверка». Дальше — остановись и опиши мне проблему.

## Сколько агентов запускать
- Простая задача (правка в 1–3 файлах): анализ и исследование может сделать сам оркестратор; developer + code-reviewer обязательны.
- Сложная задача: несколько исследователей или разработчиков — только если их части действительно независимы и не трогают одни и те же файлы.
- Параллельные разработчики в одном репозитории — только в отдельных git worktree.

## Баги
Упрощённый путь: воспроизвести и найти причину → исправить → проверить. Итог в отчёте: подтверждено / частично / не подтверждено.
