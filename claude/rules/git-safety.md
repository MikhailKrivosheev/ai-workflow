# Безопасность Git

## Перед любыми изменениями
- Выполни `git status` и узнай текущую ветку.
- Есть незакоммиченные изменения, которые сделал не ты, — это моя работа. Не трогай их и не включай в свою задачу. Если они мешают — остановись и спроси.

## Запрещено без моего явного разрешения
- `git push` в любом виде. Merge Request создаётся только вместе с одобренным push (см. «Ветки и Merge Request»).
- `git reset --hard`, `git checkout -- <файл>`, `git restore` чужих изменений, `git clean`.
- `git stash` (в том числе автоматический).
- `git rebase`, `git commit --amend` уже опубликованных коммитов, `--force` / `--force-with-lease`.
- Удаление веток и worktree, в которых есть незакоммиченная работа.
- Переключение ветки, если в рабочей папке есть незакоммиченные изменения.
- `--no-verify` и любой обход git-хуков.

## Коммиты
- Добавляй файлы явно по путям: `git add <файл>`. Не используй `git add -A` / `git add .`.
- Перед коммитом покажи себе `git diff --staged` и убедись, что там только файлы задачи.
- Сообщение коммита — всегда на английском, никогда на русском. Это моё постоянное указание: оно важнее правил проекта и истории `git log`, даже если там коммиты на русском.
- Формат сообщения (префиксы, шаблон) и имя ветки — по правилам проекта. Нет правил — по истории `git log`.
- Не коммить секреты, `.env`, локальные конфиги, артефакты сборки.

## Ветки и Merge Request — для любых правок
Моё постоянное указание для всех проектов (с 2026-11-27). Важнее правил проекта и старых уроков; если проект требует иного — спроси меня.
- Любая правка, даже одна строка, — только в отдельной ветке и только через Merge Request.
- Не коммить и не пушь напрямую в базовые и общие ветки: `develop`, `main`, `master`, `release/*`, `hotfix/*`, общую ветку раздела или редизайна. Push вида `<ветка>:develop` (перемотка базовой ветки) — тоже нельзя.
- Мелкая правка после слияния задачи — новая ветка от свежей базовой, старую ветку задачи не переиспользуй.
- Перед коммитом проверь `git branch --show-current`: если это базовая или общая ветка — остановись и создай ветку задачи.
- MR создаётся в момент push, после моего «да»; моё «да» на push — это и согласие на MR в целевую ветку:
  `git push -u origin <ветка> -o merge_request.create -o merge_request.target=<базовая> -o "merge_request.title=<заголовок>"` (GitLab).
  Push options не сработали или это не GitLab — дай мне ссылку на создание MR из ответа сервера.
- Целевая ветка MR — та, от которой создана ветка задачи. Сливаю MR я; агент MR не сливает и не одобряет.

## Ветки и worktree
- Базовую ветку определяй по правилам проекта; если неясно — по `git log` и remote, а при сомнении спроси.
- Для параллельной работы в одном репозитории используй отдельный git worktree. Создавай его от нужной базовой ветки явно.
- Не создавай worktree «на всякий случай».
